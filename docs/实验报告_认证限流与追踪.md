# 实验报告 · 认证 / 限流 / 链路追踪

> 补的是"能跑"和"能交给别人用"之间的三件事。选它们不是因为流行，而是因为它们覆盖了
> 后端接口的三道门：**谁能进（认证）**、**进多快（限流）**、**出问题怎么查（追踪）**。
>
> 三件都做成了默认开启、可关、可观测，并且每一条都有测试钉住。

## 1. 认证：JWT + 角色

### 1.1 设计

| 决定 | 理由 |
| --- | --- |
| 单独一张 `app_users` 表 | `testers` 是业务实体（谁去执行），`app_users` 是访问凭证（谁能调接口），生命周期不同：测试员离职要停账号，但历史执行记录必须留着 |
| PBKDF2-SHA256 存口令（`pbkdf2_sha256$轮数$盐$哈希`） | 标准库就有，不引编译依赖；盐和轮数一起存，方便以后升级强度 |
| HS256 + `TDP_JWT_SECRET` | 单体服务没有第三方验签方，RS256 只增加复杂度 |
| token 里只放 `sub/role/exp` | 权限清单不进 token：权限变了旧 token 到期前照旧，这是预期行为（短 TTL 兜底），不是 bug |
| 不做黑名单 | 停用账号后已签发的 token 到期前仍有效。要立刻失效需要黑名单/版本号，那是另一套东西 |
| 登录失败**统一** `invalid_credentials` | 区分"用户不存在/密码错"会让接口变成用户名枚举器 |

### 1.2 角色模型：按 HTTP 方法分级

一个路由器里既有 `GET /v1/defects` 也有 `POST /v1/defects`，路由器级只挂一个角色必然错：
要么 viewer 读不了列表，要么 viewer 能提单。

```text
GET  → 至少 viewer
写   → 至少 tester
/v1/jobs/* 和 /v1/admin/* → 至少 admin（汇总、对账、死信重放会影响全库数据）
/v1/auth/token → 公开（否则没法冷启动）
```

角色是"至少"关系：`admin > tester > viewer`，`require_roles("tester")` 表示 tester 及以上。

### 1.3 验证矩阵（都有测试）

| 场景 | 期望 | 实测 |
| --- | --- | --- |
| 不带 token | 401 `unauthorized_missing` + `WWW-Authenticate: Bearer` | ✅ |
| 乱写 token | 401 `unauthorized_invalid` | ✅ |
| 过期 token | 401 `unauthorized_expired` | ✅ |
| 换密钥签的 token | 401 `unauthorized_invalid` | ✅ |
| viewer 写业务 | 403 `forbidden`（`detail.need=tester`） | ✅ |
| tester 调管理员接口 | 403 | ✅ |
| 账号停用 | 401（登录时就挡住） | ✅ |
| `TDP_AUTH=off` | 匿名按 admin 通过（内网联调） | ✅ |

## 2. 限流：令牌桶

### 2.1 为什么是令牌桶

窗口计数在边界会放过 2 倍流量（前一窗末尾 + 后一窗开头）；令牌桶按速率匀速补，
边界没有突变，而且**桶容量天然就是"允许的突发量"**。

### 2.2 三个刻意的决定

1. **按"是谁"分桶**：有 token 按用户，没有按 IP。全局限流会让一个客户端拖垮所有人。
2. **探针与指标豁免**：`/healthz` `/readyz` `/metrics` 不能限 —— K8s 每 10s 探活，
   被 429 判死就是自己造故障。
3. **拒绝带 `Retry-After`**：不给的话客户端只能瞎重试，反而放大流量。

进程内实现、单实例有效；多副本要换 Redis（Lua 或 INCR+EXPIRE），这一点写进了代码注释和 README。

### 2.3 验证

```text
配额 3/60s：请求 1..4 → 200 200 200 429
429 响应体 {"error":"rate_limited","detail":{"limit":3,"window_seconds":60,"retry_after":N},...}
响应头 Retry-After / X-RateLimit-Limit / X-RateLimit-Remaining
/healthz × 5、/metrics × 5 → 全部 200（豁免生效）
admin 打满后 tester 仍然 200（分桶隔离）
```

## 3. 链路追踪：OpenTelemetry + W3C traceparent

### 3.1 为什么用 `traceparent` 而不是自造 header

网关、Service Mesh、前端 RUM 都认 W3C 格式。自造的 `X-Trace-Id` 到头来还要在边界做转换。
项目里两个 ID 并存，职责不同：

| 头 | 给谁看 | 用途 |
| --- | --- | --- |
| `X-Request-ID` | 人 | 日志里 `trace_id=...` 能直接搜到这一次请求 |
| `traceparent` | 追踪系统 | 跨服务/跨进程把链路拼起来 |

### 3.2 实现要点

- `TracerProvider` + `ParentBased(AlwaysOn)`：上游带了 `traceparent` 就跟着上游的采样决定。
- **默认不导出**：没配 `TDP_OTLP_ENDPOINT` 时只生成本进程 span，不产生任何网络请求 ——
  本地开发和 CI 不该因为"没起 collector"变慢或报错。配了就 `BatchSpanProcessor` 导出到 OTLP。
- 响应头回写 `traceparent`：调用方下次带着它，就能把两次请求串成一条 trace。
- **异常记在 `_observe` 而不是最外层**：本项目 `_observe` 中间件会兜底把异常变成统一 500 JSON，
  异常到最外层时已经是"一个 500 响应"了；真正的捕获点才拿得到堆栈。
- 状态标记**不降级**：内层已标 ERROR 时，外层不会用 OK 覆盖。

### 3.3 验证

```text
响应头 traceparent = 00-<32hex>-<16hex>-<flags>      （格式断言）
带上游 traceparent 请求 → 返回的 trace id 与上游一致、span id 不同（续链路）
span 属性：http.request.method / url.path / http.response.status_code / tdp.request_id
500 → span status=ERROR 且带 exception 事件（堆栈）
429 → span status=OK（4xx 是客户端问题，不是服务端故障）
```

## 4. 三件一起上之后，压测数字变了

HTTP 压测（40 并发，见 `bench/http_load.py`）：

| 场景 | P50 | P95 | P99 |
| --- | --- | --- | --- |
| 写 · service 层（不过 HTTP） | 119ms | 189ms | 260ms |
| 写 · HTTP 层（带认证 + 限流 + 追踪） | 323ms | 342ms | 344ms |
| 读 · HTTP（缓存命中） | 68ms | 135ms | 137ms |

**+84ms 的 P99 增量**里有三块：anyio 线程池排队、序列化/socket，以及新增的
JWT 解析（HS256 验签）和 trace span 创建。其中线程池排队是大头（见 `docs/实验报告_工程化.md`）。

一个真实踩到的坑：**压测前必须把限流放宽**。默认 600/分钟，而一次压测跑 600+ 请求，
不放开的话测出来的是"限流器多快"——第一版读请求全是 429，缓存命中率 0%。
`bench/http_load.py` 现在会在拉起服务时把 `TDP_RATE_LIMIT` 调到 100 万。

```bat
dev.cmd init            :: 建表（含 0003 迁移）+ 演示账号 admin/tester/viewer
```

环境变量：

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `TDP_AUTH` | `on` | `off` 时匿名按 admin 放行（仅内网联调） |
| `TDP_JWT_SECRET` | 开发默认值（会告警） | **生产必须设置** |
| `TDP_JWT_TTL` | `3600` | token 有效期（秒） |
| `TDP_RATE_LIMIT` / `TDP_RATE_WINDOW` | `600` / `60` | 每窗口请求数与窗口秒数 |
| `TDP_RATE_LIMIT_ENABLED` | `on` | `off` 关闭限流 |
| `TDP_OTLP_ENDPOINT` | 空 | 配了才把 span 导出到 collector（gRPC 4317） |
| `TDP_TRACE_CONSOLE` | 空 | 设为 1 时把 span 打到控制台（调试用） |

## 8. 补充：Redis 全局限流（多副本）

进程内的桶在多副本下是"各限各的"：3 个副本 × 600/分钟 = 实际放行 1800。
把桶放进 Redis 才能全局配额，关键是**判断与扣减必须原子**。

**为什么用 Lua 而不是 `INCR + EXPIRE`**：INCR 是固定窗口，窗口边界能放过 2 倍流量
（前一窗末尾一波 + 后一窗开头一波）。Lua 里一次做完"取时间 → 补令牌 → 判断 → 扣减 → 回写"，
整段在 Redis 单线程里执行，语义和进程内令牌桶完全一致。

**降级策略**：Redis 不可用时退回进程内桶并计数（`tdp_rate_limit_fallbacks_total`）。
限流不准 << 服务全挂；但"降级"这件事必须能被看见，否则你以为是全局限流，其实是各限各的。

配置：`TDP_RATE_LIMIT_BACKEND=auto|redis|memory`（默认 auto：Redis 通就用 Redis）。

验证（`tests/test_rate_limit.py`）：

```text
两个 RedisLimiter 实例（模拟两个副本）共享同一份配额：5 次里第 6 次被拒
20 个线程同时抢容量 10 的桶 → 恰好 10 个通过（证明 Lua 原子，没有超发）
Redis 不可用 → 降级到进程内桶，行为与单机一致
TDP_RATE_LIMIT_BACKEND=memory → 强制单机模式
```

## 9. 补充：ABAC（按项目隔离的行级权限）

RBAC 回答"这个人能不能写"，ABAC 还要回答"这条数据是不是他的项目"。
很多项目的漏洞就在这一层：一个 tester 能改别人项目的档期，只因为"他是 tester"。

### 9.1 数据模型

`project_members (project_id, username)` + 唯一约束。admin 不进成员表（直通）。
角色与成员关系正交：同样是 tester，A 在 U8 项目、B 在另一个车型项目。

### 9.2 三个攻击面与应对

| 攻击面 | 例子 | 应对 |
| --- | --- | --- |
| 显式传别人的 `project_id` | `POST /v1/bookings {project_id: 别人的}` | 从 body 取 project_id 校验成员关系 |
| 只给资源 ID | `POST /v1/queue/claim {task_id}`、`POST /v1/defects/{no}/transition` | **反查**任务/问题单/预约单属于哪个项目再校验，绝不信任客户端传的 project_id |
| 列表接口不传 project_id | `GET /v1/defects` | 按成员关系过滤；**空成员关系必须真的返回空页** |

最后一条是最典型的 ABAC 漏洞：实现成"空集合就不加 where"，等于谁都能看全部。
代码里把 `None`（管理员，不过滤）和 `set()`（空，必须过滤成空）的语义写死，
并且有一条专门的用例盯着它。

### 9.3 验证（`tests/test_abac.py`，13 条）

```text
非成员预约/提单/排队 → 403 project_forbidden（detail.action 说明是哪个动作）
成员操作自己的项目 → 201/200
非成员领取/提交别人的任务 → 403（按 task_id 反查）
非成员看/流转别人的问题单 → 403（按 defect_no 反查）
列表只返回自己项目的数据（两个项目各一条问题单，只看到自己的）
显式带别人的 project_id 过滤 → 403
零成员关系 → 空列表（不是全部）
admin → 看得到所有项目
```
