# 实验报告 · 占用方案 P99 + 深分页（50 万条）

> 技术方案 §4.1（三种占用方案的 P99）和 §4.7（50 万条 keyset 深分页）。
>
> 两件事放在一起，因为它们共用同一个结论：**正确性靠约束，性能靠索引** ——
> 换个抢占手段（§4.1）或换个翻页方式（§4.7）只是换"怎么用"，一旦索引/约束没跟上，
> 性能就还回去了。

## 2. 三种占用方案：同一套业务代码，只换"怎么抢"

`create_booking(scheme=...)` 三种取值，**幂等、建单、回填、取消完全共用**：

| scheme | 抢占方式 | 代价 |
| --- | --- | --- |
| `conditional`（A，默认） | 一条 `UPDATE ... WHERE status='free'`，用 affected rows 定胜负 | 无额外往返 |
| `pessimistic`（B） | 事务内 `SELECT ... FOR UPDATE` 锁行，再判断/更新 | 多一次往返 + 多一次锁 |
| `redis`（C） | 先 `SET NX EX` 预占，抢到的才写库 | Redis 一次往返；多一层要维护 |

C 的两条硬规则（写在 `app/infra/redis_lock.py` 里）：

1. **Redis 只是漏斗，不是真相**。预占成功后仍然走数据库的条件 UPDATE，
   最终"谁赢"由唯一约束决定。
2. **预占失败要放掉，取消要放掉**。否则档期会被"幽灵占位"卡到 TTL 过期 ——
   表现是"取消了却约不回来"，这是最难查的一类 bug。取消时用 `force_release`
   （不看 holder 直接删），因为取消是数据库层的确定事实。

## 3. P99 结果

```text
占用方案 P99 对比 · 并发 100 · 每方案 3 轮

  方案                  P50      P95      P99      max     DB 语句
  A 条件更新          224.42ms  249.43ms  268.59ms  268.59ms       603
  B 悲观锁           253.92ms  267.47ms  275.41ms  275.41ms       604
  C Redis 预占         9.51ms   15.32ms   25.12ms   25.12ms         9
```

| 指标 | A 条件更新 | B 悲观锁 | C Redis 预占 |
| --- | --- | --- | --- |
| P50 | 224ms | 254ms | **9.5ms** |
| P99 | 269ms | 275ms | **25ms** |
| 打到 DB 的 SQL 语句数 | 603 | 604 | **9** |
| 成功数 | 1 | 1 | 1 |

**怎么读这张表：**

- **正确性三者一致**：100 个并发抢同一个档期，成功恰好 1 个（3 轮都断言了
  `created=1` 且库里 `bookings` 只有 1 条有效记录）。这是约束给的，不是方案给的。
- **A 和 B 几乎一样**。B 多了一次 `SELECT ... FOR UPDATE`，但在"单档期"场景里
  它锁的正是 A 接下来要更新的那一行 —— 多花的钱没买到任何东西。
  B 的价值在"连续占多个半天 + 先查后改"的复杂逻辑：一次锁住、判断完再统一更新。
- **C 快一个数量级**，原因不是"赢家更快"（赢家照样要写库），而是
  **99 个输家一次 DB 都没打**：DB 语句数 603 → 9，降了 67 倍。
  这正是抢购式峰值的正确用法 —— 把无效流量挡在数据库外面。

**代价必须说清楚**：C 多了一个 Redis 依赖和一个 TTL 窗口。
Redis 挂了会自动降级成"直连 DB"（`reserve()` 返回 None 时走 A 的路径），
降级后行为与 A 完全一致，只是没了那一层漏斗。

## 4. 深分页：50 万条，`OFFSET` vs **keyset**

### 4.1 全局列表（索引正好命中）

```text
       页深   OFFSET P50   OFFSET P99   KEYSET P50   KEYSET P99       加速
        1        0.90ms       12.41ms        0.76ms        1.40ms     8.8x
     1000        5.25ms        6.51ms        0.83ms        1.26ms     5.2x
    10000      346.51ms      392.43ms        0.82ms        1.37ms   287.3x
    25000      103.39ms      148.11ms        0.75ms        1.15ms   128.4x
```

- **OFFSET 随页深线性变慢**：第 1 页 12ms、第 25000 页 148ms（第 10000 页那次
  撞上了统计信息/缓存抖动，392ms，如实保留）。它就是"扫描 + 丢弃"，翻得越深越亏。
- **KEYSET 基本恒定**：1.15~1.40ms，第 25000 页和第 1 页没有区别。
  `EXPLAIN (ANALYZE, BUFFERS)` 证明它走的是
  `Index Scan using ix_defects_keyset`，**Buffers: shared hit=4**（只碰 4 个页）。

### 4.2 这一节才是重点：keyset 不是"改 SQL 就快"

API 的列表接口几乎总是带 `project_id` 过滤。基线里只有
`ix_defects_keyset (created_at DESC, id DESC)` —— **只覆盖排序，覆盖不了过滤**。
同一句 keyset SQL，只是索引不同：

```text
带 project_id 过滤（无复合索引）
        1       98.28ms      124.79ms       94.70ms      113.19ms     1.1x
     1000      100.64ms      107.04ms      109.00ms      110.68ms     1.0x
    10000      168.84ms      173.04ms       76.51ms       80.08ms     2.2x
    25000      186.26ms      191.47ms        0.78ms        1.29ms   148.6x

带 project_id 过滤（有复合索引 ix_defects_project_keyset）
        1        0.79ms        3.54ms        1.06ms        1.49ms     2.4x
     1000        3.37ms        3.74ms        0.85ms        1.09ms     3.4x
    10000       24.67ms       25.65ms        0.78ms        1.75ms    14.6x
    25000       59.70ms       65.58ms        0.79ms        1.47ms    44.6x
```

**没有复合索引时，keyset 在浅页（113ms）甚至比 OFFSET 还差** ——
因为 PG 只能"扫项目下的行 → 过滤 → 排序"，全表 50 万行里该项目的行它都得过一遍。
加上复合索引后，浅页从 **113ms → 1.5ms**，而且**深页依然恒定在 1.5ms**。

索引已经落在 [`migrations/versions/002_perf_indexes.sql`](../migrations/versions/002_perf_indexes.sql)：

```sql
CREATE INDEX IF NOT EXISTS ix_defects_project_keyset
    ON defects (project_id, created_at DESC, id DESC);
```

> 一句话：**keyset 的收益来自"索引能同时满足过滤和排序"**。
> 只把 `OFFSET` 改成 `(created_at, id) < (?, ?)` 但索引没跟上，
> 生产上很可能是"换了个写法，没变快"，而且没人发现。

同一份 002 迁移里还补了三条对账/清理用的索引（`defect_links(execution_id)`、
`defects(execution_id) WHERE NOT NULL`、`idempotency_keys(created_at)`）——
`fail_without_defect` 要按 `execution_id` 反查，幂等键清理要按时间删，
原来都是全表扫。

### 4.3 正确性

同一个深度，两种方式必须返回**同一页**（20 条 id 完全一致）：`True`。

这里踩过一个 off-by-one：keyset 的游标应该是**上一页最后一条**，不是当页第一条。
取错的话返回的是下一整页，而且"翻页看起来正常"，只有对比才会发现。

## 6. 本项**没有**做的

| 项 | 说明 |
| --- | --- |
| 1000 并发下的 P99 | 1000 线程在这台 16 核机器上会 CPU 饱和，测出来是调度噪声（缓存实验那轮已经踩过）。正确性用了 1000 并发（`bench/slot_contention.py`），P99 用 100。 |
| 多副本下的 C | 多副本共享 Redis，预占全局有效；但"预占成功、实例崩溃"要靠 TTL 兜底，没有做跨实例的补偿。 |
| keyset 的并发插入抖动 | 深分页期间如果有新数据插到前面，keyset 会稳定不漏（这是它的优点），但"总页数"不再是稳定概念。这是 keyset 的固有语义，不是 bug。 |
| 分页压测的 P99 归因 | 数字里含连接池/会话开销；结论看的是**同一口径下的相对差异**，不是绝对延迟。 |
