## 2. 明确不做的事（附理由）

| 项 | 为什么不做 |
|---|---|
| **token 刷新 / 登出** | 内部工具、单服务，TTL 1 小时够用。要做刷新得引 refresh 轮换 + 黑名单，复杂度与收益不匹配。 |
| **字段级权限** | 权限做到项目级就停了——业务边界就是项目。再往下是策略引擎（OPA/Casbin），会为一个不存在的需求引入依赖。 |
| **租户级配额** | 限流按用户分桶。项目 ≠ 租户，硬造租户模型只为讲"分布式"，属于自欺。 |
| **WebSocket / 长连接** | 页面是低频操作（看档期、领任务），轮询/刷新足够；上 WS 只增加连接管理与调试成本。 |

## 3. 已知边界（生产环境要补，演示环境可接受）

| 边界 | 现状 | 生产做法 |
|---|---|---|
| 数据库备份 | 没做 | `pg_dump` 定时 + WAL 归档；演示库可用 `init_db --drop` 重建 |
| SLO / 错误预算 | 有 P99 实测数字，没写成 SLO | 定 `/v1/queue` P99 < 300ms、5xx < 0.5%，配 Prometheus 告警（规则已有 7 条） |
| 长稳压测 | 10 项压测里没有 soak | 4 小时阶梯压测看内存/连接池是否泄漏 |
| Grafana 实机 | 13 面板配置齐全，本机没 Docker 未实跑 | `compose --profile monitoring up` 后截图；CI 起不了 Grafana |
| 审计日志 | 只有业务表 + transition 记录，没有"谁重放了死信"这类运维审计 | 敏感操作单独建审计表 |
| 数据保留 | 幂等键有 TTL（调度器每 6h 清理），执行记录只增不减 | 按业务保留期归档到历史表 |

## 4. 压测口径（避免被问"你这个数可信吗"）

- **1000 并发**用于验**正确性**（重复占用 0、成功恰好 1），打的是 service 层，不含 uvicorn；
- **P99** 用 100 并发测，因为 1000 线程在这台机器上本身就是调度噪声；
- **HTTP 层**单独测过：service 297ms vs HTTP 379ms，差的 80ms 是 anyio 线程池 + DB 连接池两级排队，不是框架开销；
- 结论：这些数字**只能横向比较**（方案 A vs B vs C），不能当绝对延迟承诺。

## 5. 一句话总结

> 功能与工程质量都足以支撑"按生产标准做的服务"这个说法；
> 缺的都是**单机演示环境不需要、真上生产才需要**的那一层，且每条都有明确的补法。
