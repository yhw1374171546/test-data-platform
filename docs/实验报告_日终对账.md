# 实验报告 · 日终对账

> 目标：技术方案 §4.6 —— **三方对齐**（明细 / 汇总 / 质量规则），
> 验收线：**"注入 5 种差错 → 检出 100%、误报 0"**。
>
> 本报告只记录实际跑出来的输出。

---

## 1. 三方分别是什么

| 侧 | 数据源 | 回答的问题 |
| --- | --- | --- |
| ① 明细 | `executions ⋈ execution_queue`，按 (本地日, 项目, 版本) 聚合 | 到底跑了多少、结果分布如何 |
| ② 汇总 | `daily_exec_summary` | 日报上写的是多少 |
| ③ 质量 | `result='fail'` 且**没有任何关联问题单**的执行 | 失败有没有走完提单流程 |

第 ③ 条是这个项目里最值得讲的一条：
**它检查的不是数据一致性，而是流程有没有被遵守**。数字全对、但失败没提单，
报表一片绿，质量事故就这么被漏掉了。纯数字对账永远发现不了它。

### 四类差异

| kind | 含义 | 业务后果 |
| --- | --- | --- |
| `missing_summary` | 有明细无汇总 | 少算 |
| `extra_summary` | 有汇总无明细 | 多算 / 脏数据 |
| `summary_mismatch` | 逐列比对不一致（`total/passed/failed/blocked`） | 日报口径错 |
| `fail_without_defect` | 失败但没提单 | **质量问题被漏掉** |

### 一个必须写死的口径

`daily_exec_summary` **没有 `skipped` 列**，所以 `total` 含 `skip`，
`passed + failed + blocked <= total` 是正常的（差值就是 skip 数）。
对账只比这四列，**不要**试图让它们相加相等 —— 否则每天每个 skip 都会变成一条假差异。
这条在 `tests/test_recon_rules.py::test_skip_only_in_total_is_not_a_discrepancy` 里钉住了。

## 2. 实验：注入 5 种差错

**脚本**：`bench/recon_inject.py`　**命令**：`python bench/recon_inject.py`

做法：先造一个"完全正确"的项目（6 天数据，fail 全部带缺陷），确认对账**一条都不报**；
然后逐天注入差错，看是否都能检出。

### 原始输出

```text
对账注入实验：5 种差错 · 检出率 100% · 误报 0

[基线] 6 天数据全部正确 → 差异 0 条（[]）
    [OK] 误报 0：干净数据一条都不报

[注入] 5 种差错，逐条核对检出情况：
    [OK] ① 漏汇总          期望 missing_summary      检出
    [OK] ② 多汇总          期望 extra_summary        检出
    [OK] ③ 数字改错         期望 summary_mismatch     检出
    [OK] ④ 失败未提单        期望 fail_without_defect  检出
    [OK] ⑤ 跨日-原日        期望 extra_summary        检出
    [OK] ⑤ 跨日-次日        期望 missing_summary      检出

[结论] 检出 6/6 条，误报 0 条，漏检 0 条
    [OK] 检出率 100% 且误报 0

[差异单] 共 6 条（一次对账写入/更新 6 行）
    2024-11-16  missing_summary      expected=2 actual=0  有明细无汇总（少算）
    2024-11-17  extra_summary        expected=0 actual=4  有汇总无明细（多算）
    2024-11-18  summary_mismatch     expected=2 actual=3  汇总与明细数字不一致
    2024-11-19  fail_without_defect  expected=1 actual=0  执行失败但未提问题单
    2024-11-20  extra_summary        expected=0 actual=1  有汇总无明细（多算）
    2024-11-21  missing_summary      expected=1 actual=0  有明细无汇总（少算）

  结论：全部通过
```

### 结论

| 指标 | 目标 | 实测 |
| --- | --- | --- |
| 检出率 | 100% | **6/6 条（5 种差错，跨日产生 2 条）** |
| 误报 | 0 | **干净数据 + 修好后重跑都是 0** |
| 差异单可读性 | 能直接定位 | 每条都带 `expected/actual` 和具体的 `execution_ids` / 逐列 `diff` |

### ⑤「跨日」为什么算两种差异

把某天 01:00 的执行挪到次日 00:30 之后，**同一份数据在两个业务日都错了**：

```
原日：明细没了、汇总还在   → extra_summary（多算）
次日：明细来了、汇总没有   → missing_summary（少算）
```

所以对账必须**按天各自核对**；只跑一天只能看到一半问题。
实验里也验证了这一点：只对原日跑 → 只报 1 条。

> 这也是技术方案 §9 坑 #4（时区口径）的现实版本：
> 如果明细侧用 UTC 日、汇总侧用本地日，每天 00:00~08:00 的执行都会"跨日"，
> 于是每天都会有一条 `extra_summary` + 一条 `missing_summary`。现在两侧共用
> `biz_time.biz_date_sql()`，口径一致才不会自己制造差异。

## 3. 差异单是「活」的

`recon_discrepancies` 上有 `UNIQUE (biz_date, project_id, kind)`：

- 重复跑对账只更新 `expected/actual/detail`，**不会堆出一堆历史噪音**；
- 问题修好后再跑一次，`resolved` 自动变 `true` —— **不需要人工点"已解决"**。

这里踩过一个坑（已修，见 README 踩坑表第 16 条）：
最初的 `_resolve_stale` 只遍历"本次发现有差异的组合"，
结果问题修好后**没有差异了**，那段代码压根不会执行，旧差异单永远挂着 unresolved。
正确做法是把"本次检查过的组合"（含没有差异的）作为作用域传进去。

## 5. 复现

```bat
dev.cmd recon     :: 全量重对（加 --strict 时，有差异退出码 1，可挂调度系统）
dev.cmd bench     :: 五项实验，含对账注入
dev.cmd test      :: 131 个用例
dev.cmd smoke     :: 36 项真实 HTTP 冒烟
```

单独跑：

```powershell
python bench/recon_inject.py
python scripts/recon.py --biz-date 2025-06-09 --project-id 1
python -m pytest tests/test_recon_rules.py tests/test_recon_flow.py -q
```

> `dev.cmd recon` 全量跑会报出压测故意注入的差错样本（`BENCH-*` 项目）。
> 那不是 bug，是这条规则第一次在真实数据上生效。只想看干净范围就加
> `--biz-date` / `--project-id`。

## 6. 本项**没有**做的

| 项 | 说明 |
| --- | --- |
| `defect_links(execution_id)` / `defects(execution_id)` 索引 | 质量侧用 `NOT EXISTS` 子查询，目前没有 `execution_id` 单列索引。数据量上来（十万级 fail）会全表扫，需要补两个索引 —— 留给"深分页 + 索引"那一轮一起做，并附 `EXPLAIN` |
| 差异单的处置流程 | 现在只有"自动解决"，没有"人工标记误报"/备注/指派。真实运维需要，但不是技术考点 |
| 对账的历史趋势 | 只有当前状态，没有"差异数随时间"的曲线（Prometheus gauge 已有 `tdp_recon_discrepancies{kind}`，接 Grafana 即可） |
| 跨项目同步对账 | 技术方案里"跨项目执行结果同步"没有实现（本项目没有真正的多实例场景） |
