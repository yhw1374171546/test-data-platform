# 实验报告 · 任务领取（乐观锁抢占）

> 目标：技术方案 §4.2 的验收线 —— **"20 个测试员并发领同一条任务 → 恰好 1 人；同 key 重放返回同一个结果；换 body 同 key → 422"**。
>
> 本报告只记录**实际跑出来的输出**。没测的项（P99 延迟）在文末单列，不混进结论。

## 1. 一条 UPDATE 定胜负

```sql
UPDATE execution_queue
   SET status = 'claimed', claimed_by = :t, claimed_at = now(), version = version + 1
 WHERE id = :id AND status = 'pending' AND version = :v
RETURNING version, claimed_at
```

- `WHERE status='pending'` 保证"同时抢只有一人成功"：PG 在 READ COMMITTED 下会对
  **被阻塞的 UPDATE 重新求值谓词**，后到的事务醒来发现 status 已不是 pending，`affected=0`。
- `version=?` 防的是 **ABA**：`领取(v1) → 释放(v2) → 再领取(v3)` 之后，
  一个还拿着 v1 的客户端重放请求，只靠 status 会以为"我领到了"，实际上任务已经易主。
- `affected=0` 之后**必须重读一次**，才能区分两种完全不同的失败：

| 重读结果 | 返回 | 客户端该做什么 |
| --- | --- | --- |
| 状态已不是 pending | 409 `already_claimed` | 换一条任务 / 等对方释放 |
| 仍是 pending 但版本变了 | 409 `version_conflict` | 重读版本号后立即重试 |

## 2. 实验：20 并发（四组）

**脚本**：`bench/claim_race.py`　**命令**：`python bench/claim_race.py --concurrency 20`

每组用**全新的任务 + 全新的测试员**，互不干扰。

### 原始输出

```text
==========================================================================
任务领取竞争压测 · 并发 20
==========================================================================

[A] 20 个测试员 × 20 个**不同**幂等键抢同一任务
    结果分布: {'claimed': 1, 'already_claimed': 19}
    落库状态: status=claimed version=1 claimed_by=487
    耗时(整批墙钟): 94 ms
    [OK] 恰好 1 人领到，version 只 +1

[B] 同 1 个测试员 × **同一个**幂等键并发 20 次
    结果分布: {'claimed': 1, 'replayed': 19}
    落库状态: status=claimed version=1
    耗时(整批墙钟): 25 ms
    [OK] 恰好 1 次真实领取，其余全部重放（version 只 +1）

[C] 同幂等键换 body（换一个测试员）
    首次: claimed  第二次: body_mismatch/422
    落库 claimed_by=489（要求仍是第一个测试员 489）
    [OK] 换 body 被 422 拒绝且无副作用

[D] ABA 保护：领取(v1) → 释放(v2) → 旧版本号重领 → 新版本号重领
    旧版本号(v0)重领: version_conflict
    新版本号(v2)重领: claimed version=3
    落库状态: status=claimed version=3
    [OK] 陈旧请求被 409 version_conflict 拦住

==========================================================================
  结论：全部通过
==========================================================================
```

### 结论

| 指标 | 目标 | 实测 |
| --- | --- | --- |
| 成功领取数 | 恰好 1 | **1**（`claimed=1`） |
| 其余请求 | 全部 409 | **19 条 `already_claimed`**，无 500 / 无死锁 |
| `claimed_by` | 只有一个 | **只有一个**，且 `version` 只 +1 |
| 同 key 重放 | 同一个结果 | **1 claimed + 19 replayed**，`version` 仍是 1 |
| 换 body 同 key | 422 且无副作用 | **422**，`claimed_by` 未变 |
| ABA | 陈旧请求被拒 | **409 `version_conflict`**，之后用 v2 领到 v3 |

> 说明：`耗时(整批墙钟)` 是"20 个线程全部跑完"的实际耗时，**不是 P99**。
> P99 需要逐请求采样，放在本项技术点的方案对比里一起做（见文末）。

### 并发 50 的对照

```text
[A] 结果分布: {'claimed': 1, 'already_claimed': 49}
[B] 结果分布: {'claimed': 1, 'replayed': 49}
```

形状与 20 并发完全一致，说明结论是**机制性**的（来自 `WHERE status='pending'`），不是并发数凑巧。

## 3. 关于技术方案原文那句话

原文写的是："20 个测试员并发领**同一条**任务，**同 `Idempotency-Key`**"。

这句话里其实是**两套机制**，硬写在一个用例里会互相打架，所以拆成两组：

| 场景 | 考的是什么 | 期望 |
| --- | --- | --- |
| 20 个不同测试员、**不同** key | `WHERE status='pending'` 的原子性 | 1 成功 + 19 个 `already_claimed` |
| 同 1 个测试员、**同** key 并发 | 幂等键（`idempotency_keys` 唯一约束） | 1 次真实领取 + 19 次重放 |

为什么不能混着写：`body_hash` 里包含 `tester_id`，**不同测试员 + 同 key 就是"同 key 换 body"**，
第二个请求会被 422 挡掉——那测到的是 body 校验，不是抢占。
"换 body → 422" 因此单独作为 C 组验证。

## 7. 本项**没有**测的（避免夸大）

| 项 | 原因 | 计划 |
| --- | --- | --- |
| **逐请求 P99** | 现有 bench 只采结果分布与整批墙钟；不臆造延迟数字 | 与 A/B/C 三种占用方案一起补采样 |
| 领取超时自动释放 | 需要后台扫表（`claimed_at + TTL`），属于 worker 范畴 | 和 outbox worker 一起做 |
| 领取与"当天有档期"的联动 | 真实业务里领任务应校验该测试员当天有车（booking） | 与 `/v1/executions` 一起设计，避免现在定错耦合 |
