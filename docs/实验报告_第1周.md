# 第 1 周实验报告 · 档期竞争与问题单状态机

> 目标：技术方案 §6 第 1 周的验收线 —— **"1000 并发抢同一档期 → 重复占用 0、成功恰好 1"**，
> 以及 §4.5 的 **"遍历所有 (from,to) 组合 → 合法全过、非法全 409、审计条数 == 合法转移数"**。
>
> 本报告只记录**实际跑出来的输出**，不含估算值。没测的项在文末单独列出来，不混在结论里。

## 1. 实验一：1000 并发抢同一档期（技术方案 §4.1）

**脚本**：`bench/slot_contention.py`　**命令**：`python bench/slot_contention.py --concurrency 1000`

三组实验各自用**全新的车辆 + 全新日期**，互不干扰：

| 组 | 场景 | 想验证什么 |
| --- | --- | --- |
| A | 1000 个**不同**幂等键抢同一档期 | 唯一约束 + 条件更新是否真的只放进去 1 个 |
| B | 1000 个**相同**幂等键并发 | 幂等是否只生效 1 次（其余全部重放） |
| C | 同幂等键换 body | 是否 422 且不产生副作用 |

### 原始输出

```text
==========================================================================
档期竞争压测 · 并发 1000
==========================================================================

[A] 1000 个**不同**幂等键抢同一档期
    结果分布: {'created': 1, 'slot_taken': 999}
    落库有效预约数: 1   （要求恰好 1）
    [OK] 重复占用 = 0

[B] 1000 个**相同**幂等键并发
    结果分布: {'created': 1, 'replayed': 999}
    落库有效预约数: 1   created=1 replayed=999
    [OK] 幂等生效（恰好 1 次真实创建，其余全部重放）

[C] 同幂等键换 body
    首次: created  第二次: body_mismatch/422
    落库预约数: 1   （要求 1，第二次不得产生副作用）
    [OK]

==========================================================================
  结论：全部通过
==========================================================================
```

### 结论

| 指标 | 目标 | 实测 |
| --- | --- | --- |
| 重复占用数 | 0 | **0** |
| 成功预约数 | 恰好 1 | **1**（`created=1`） |
| 失败原因分布 | 全部 `slot_not_available` | **999 条全是 `slot_taken`**，没有一条 500 / 死锁 |
| 同 key 并发 | 只生效 1 次 | **created=1 / replayed=999** |
| 同 key 换 body | 422 且无副作用 | **422，落库预约数仍为 1** |

> 关键点：**999 个失败里没有 500、没有 deadlock、没有 pool timeout**。
> 这说明竞争被收敛在"一条 `UPDATE ... WHERE status='free'` 的 affected rows"这一层，
> 而不是在应用层抛异常、重试、或者靠锁等待超时。失败语义干净，调用方才能写可靠的分支逻辑。

并发 200 时的对照（`dev.cmd bench -Concurrency 200`）结果形状完全一致：
`created=1 / slot_taken=199`、`created=1 / replayed=199`、C 组 422，**说明结论与并发数无关，机制性成立**。

## 2. 实验二：问题单状态机 8×8 穷举（技术方案 §4.5）

**用例**：`tests/test_defect_flow.py::test_full_matrix_legal_illegal_and_audit`

做法：对 `(from, to)` 的 **64 个组合**，每条都用**独立的缺陷单**（先绕过状态机把状态强制改成 `from`，
避免上一轮污染下一轮），然后调用真实的 `transition_defect`，逐条核对三件事：

1. 合法 → 200 `moved`，库里的状态变成 `to`；
2. 非法 → 抛 `IllegalTransition`（接层 409），**状态不变、审计不变**；
3. 自环（`from == to`）→ 200 `already=true`，**不写审计**。

最后的全局断言：

```text
assert legal_count == 15
assert audit_delta == legal_count        # 审计条数 == 合法转移数
```

实测：64 组合里 **15 条合法**（= 转移表的边数）、**41 条非法全部被拦**、
**审计新增正好 15 条**（每条合法转移 1 条，非法/重放 0 条）。

### 并发：20 个测试员同时推同一目标状态

`tests/test_defect_flow.py::test_concurrent_same_target_writes_one_audit`

```text
codes.count("moved")   == 1      # 只有一个人真正改了状态
codes.count("already") == 19     # 其余全部识别为"已经是目标状态"
len(audit_rows) - before == 1    # 审计只多 1 条
```

这一条是状态机最容易写错的地方：如果"先 SELECT 判断合法、再无脑 UPDATE"，
20 个并发会写出 20 条审计、而且返回 20 个"成功"。这里靠
`UPDATE ... WHERE id=? AND status=?` 的 affected rows 把并发收敛成 1 次真实流转。

## 3. 实验三：端到端冒烟（真实 HTTP）

**脚本**：`scripts/api_smoke.py`（对运行中的 uvicorn 发请求，不是 TestClient）

```text
端到端冒烟 · http://127.0.0.1:8010

[OK]   GET /healthz 200
[OK]   GET /readyz 200 且 db=ok
[OK]   首次预约 201 created
[OK]   同 key 重放：同一个单号 + replay=true
[OK]   换 key 抢同一档期 409 slot_not_available
[OK]   错误体带 trace_id
[OK]   取消 200 cancelled
[OK]   取消后同一档期可复用（部分唯一索引生效）
[..]   已释放本次占用的档期 2181-07-02
[OK]   提报 201
[OK]   open -> closed 非法转移 409
[OK]   409 的 detail.allowed 给出可去往状态      ['rejected', 'triaged']
[OK]   open -> triaged 200 moved
[OK]   重复提交同一目标状态：already=true（不重复写审计）
[OK]   详情含审计轨迹：创建 1 条 + 真实转移 1 条  [('(new)','open'), ('open','triaged')]
[OK]   列表接口可用（keyset 形态）
[OK]   状态机自描述：15 条合法边
[OK]   POST /metrics 200
[OK]   业务指标已打点（booking / defect）

结论：全部通过（18 项）
```

其中"取消后同一档期可复用"这条同时验证了两件事：
`bookings` 的部分唯一索引 `WHERE status='active'` 生效，
且取消时档期行被真正释放回 `free`（而不是只在预约单上打了个标记）。

> 冒烟脚本自己也踩过一个坑：早期用"2031 年内的随机日期"当档期，
> 重复运行会撞上自己上一次留下的占用，导致"首次预约"变成 409。
> 现在改成 2100 年往后 10 万天范围随机 + 真撞上就换一天重试 + 跑完取消释放，
> 连续跑两次都是 18 项全过（已实测）。
