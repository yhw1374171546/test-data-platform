# 测试数据管理平台 · 技术方案

> **定位**：个人项目（**不挂公司名下**）。起源是真人真事——我在汽车测试里天天手工拼"车辆 + 版本 + 用例 + 问题单"的数据，把这个重复劳动做成了系统。
> **技术栈**：Python 3.10+ · FastAPI · SQLAlchemy 2.x · Alembic · PostgreSQL 16 · Redis · Prometheus
> **技术重点**：**并发下的资源占用一致性**（车档期不能被两个项目同时占用、用例不能被两个人同时领取）

---

## 一、为什么这个项目"业务是真的、技术是硬的"

### 1.1 真实痛点

做整车测试时，数据散在四处：

```
测试车辆（哪台车在哪、今天有没有被排出去）
   ×  软件版本（这台车刷的是哪个版本）
   ×  测试用例（要跑哪些、谁在跑、跑到哪了）
   ×  问题单（失败的要提单、要关联到执行记录）
```

**四个维度靠人工表格拼**，典型问题：
- 同一台测试车被两个项目同时排期 → 到场发现车被开走
- 同一个用例被两个人同时领 → 重复执行、结果互相覆盖
- 执行失败了但**没提单** → 质量统计漏了
- 日报靠人肉汇总 → 口径不一致

### 1.2 技术骨架与"配件库存版"的对应关系

| 通用技术点 | 配件库存版 | **本项目（测试数据版）** |
| --- | --- | --- |
| 资源占用不超卖 | 库存扣减 | **测试车辆档期占用**（车 × 日期 × 半天 唯一） |
| 抢占式领取 | — | **执行任务领取**（用例 × 版本，恰好一人领到） |
| 幂等 | 领料扣库存 | **领取/提交结果**（同 key 20 并发只生效 1 次） |
| 缓存一致性 | 配件详情 | **车辆/用例详情** |
| 跨库最终一致 | 跨店调拨 | **跨项目执行结果同步 / 汇总落库** |
| 状态机 | 工单 | **问题单生命周期** |
| 对账 | 工单 vs 库存流水 | **执行明细 vs 日报汇总 vs 问题单** |
| 深分页 | 工单列表 | **问题单列表（50 万条）** |

> **一句话**：业务对象换了，技术考点一个没少。而且每个考点都能压测出数。

### 1.3 一个关键业务判断（写进设计里）

**"档期以半天为粒度，不做分钟级"**——这是业务决策不是技术偷懒：

| 粒度 | 优点 | 缺点 |
| --- | --- | --- |
| 分钟级 | 精确 | 区间重叠判断复杂（`tsrange` + GiST）、并发下极易冲突、测试实际按半天排 |
| **半天（上/下午）** | **唯一约束直接搞定，无重叠计算** | 粒度粗 |

**面试时主动说这一点**："我先问了业务到底按什么粒度排车，答案是'上下午'，所以我用半天粒度做唯一约束，把'区间重叠'这个复杂问题**规避掉**了，而不是硬上 `tsrange` 求交集。"

> 这比"我用了排他约束"更能体现判断力——**能不做复杂方案而达成同样效果，是更好的工程决策**。

## 二、表结构（PostgreSQL 16，已在真库跑通）

```sql
-- ═══════════════ 主数据 ═══════════════
CREATE TABLE projects (
    id         BIGSERIAL PRIMARY KEY,
    code       TEXT NOT NULL UNIQUE,              -- 如 U8-CITY-NOA-2025Q3
    name       TEXT NOT NULL,
    model      TEXT NOT NULL,                     -- 车型
    stage      TEXT NOT NULL DEFAULT 'testing'    -- testing|releasing|released|archived
);

CREATE TABLE vehicles (
    id          BIGSERIAL PRIMARY KEY,
    vin         TEXT NOT NULL UNIQUE,
    model       TEXT NOT NULL,
    plate_no    TEXT,
    status      TEXT NOT NULL DEFAULT 'available', -- available|in_test|maintenance|retired
    location    TEXT NOT NULL DEFAULT ''           -- 试验场/门店
);

CREATE TABLE versions (
    id         BIGSERIAL PRIMARY KEY,
    model      TEXT NOT NULL,
    ver        TEXT NOT NULL,                      -- 软件版本号
    released   BOOLEAN NOT NULL DEFAULT FALSE,
    UNIQUE (model, ver)
);

CREATE TABLE testers (
    id          BIGSERIAL PRIMARY KEY,
    employee_no TEXT NOT NULL UNIQUE,
    name        TEXT NOT NULL,
    team        TEXT NOT NULL DEFAULT ''
);

CREATE TABLE test_cases (
    id          BIGSERIAL PRIMARY KEY,
    case_no     TEXT NOT NULL UNIQUE,              -- TC-NOA-0123
    module      TEXT NOT NULL,                     -- 领航/泊车/HMI…
    title       TEXT NOT NULL,
    priority    TEXT NOT NULL DEFAULT 'P2',        -- P0..P3
    precondition TEXT NOT NULL DEFAULT '',
    steps_summary TEXT NOT NULL DEFAULT ''
);
CREATE INDEX ix_cases_module_priority ON test_cases (module, priority);

-- ═══════════════ ① 车辆档期（本项目核心：并发占用）═══════════════
-- 一行 = 一台车的一个半天。**占用的本质是把 status 从 free 原子改成 booked**，
-- 就像扣库存；但因为有唯一约束 (vehicle_id, slot_date, half)，
-- "同一台车同一半天只能有一个有效占用"由 DB 保证。
CREATE TABLE vehicle_slots (
    id         BIGSERIAL PRIMARY KEY,
    vehicle_id BIGINT NOT NULL REFERENCES vehicles(id),
    slot_date  DATE NOT NULL,
    half       SMALLINT NOT NULL CHECK (half IN (0, 1)),   -- 0=上午 1=下午
    status     TEXT NOT NULL DEFAULT 'free',               -- free|booked|maintenance
    booking_id BIGINT,                                     -- 占用人（预约单）
    version    BIGINT NOT NULL DEFAULT 0,                  -- 乐观锁版本
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (vehicle_id, slot_date, half)
);
CREATE INDEX ix_slots_free ON vehicle_slots (slot_date, half, status);

CREATE TABLE bookings (
    id          BIGSERIAL PRIMARY KEY,
    booking_no  TEXT NOT NULL UNIQUE,
    project_id  BIGINT NOT NULL REFERENCES projects(id),
    vehicle_id  BIGINT NOT NULL REFERENCES vehicles(id),
    testers_id  BIGINT NOT NULL REFERENCES testers(id),
    slot_date   DATE NOT NULL,
    half        SMALLINT NOT NULL CHECK (half IN (0, 1)),
    status      TEXT NOT NULL DEFAULT 'active',    -- active|cancelled|done
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- 取消后可复用同一档期：只对有效预约做唯一（部分索引）
CREATE UNIQUE INDEX ux_booking_active
    ON bookings (vehicle_id, slot_date, half) WHERE status = 'active';

-- ═══════════════ ② 执行任务池（抢占式领取）═══════════════
CREATE TABLE execution_queue (
    id         BIGSERIAL PRIMARY KEY,
    project_id BIGINT NOT NULL REFERENCES projects(id),
    version_id BIGINT NOT NULL REFERENCES versions(id),
    case_id    BIGINT NOT NULL REFERENCES test_cases(id),
    status     TEXT NOT NULL DEFAULT 'pending',    -- pending|claimed|running|done|cancelled
    claimed_by BIGINT REFERENCES testers(id),
    claimed_at TIMESTAMPTZ,
    version    BIGINT NOT NULL DEFAULT 0,          -- 乐观锁：领取时校验
    UNIQUE (project_id, version_id, case_id)
);
CREATE INDEX ix_queue_pending ON execution_queue (project_id, status);

CREATE TABLE executions (
    id          BIGSERIAL PRIMARY KEY,
    queue_id    BIGINT NOT NULL REFERENCES execution_queue(id),
    vehicle_id  BIGINT REFERENCES vehicles(id),
    tester_id   BIGINT NOT NULL REFERENCES testers(id),
    result      TEXT NOT NULL,                     -- pass|fail|blocked|skip
    note        TEXT NOT NULL DEFAULT '',
    executed_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ix_exec_summary ON executions (executed_at, result);

-- ═══════════════ ③ 问题单（状态机 + 审计）═══════════════
CREATE TABLE defects (
    id            BIGSERIAL PRIMARY KEY,
    defect_no     TEXT NOT NULL UNIQUE,
    title         TEXT NOT NULL,
    severity      TEXT NOT NULL,                   -- S1..S4
    status        TEXT NOT NULL DEFAULT 'open',
    project_id    BIGINT NOT NULL REFERENCES projects(id),
    execution_id  BIGINT REFERENCES executions(id),-- 来源执行记录（可为空=人工提报）
    owner_id      BIGINT REFERENCES testers(id),
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- 深分页必须靠它（keyset）
CREATE INDEX ix_defects_keyset ON defects (created_at DESC, id DESC);
CREATE INDEX ix_defects_project_status ON defects (project_id, status, created_at DESC);

CREATE TABLE defect_transitions (
    id         BIGSERIAL PRIMARY KEY,
    defect_id  BIGINT NOT NULL REFERENCES defects(id),
    from_status TEXT NOT NULL,
    to_status   TEXT NOT NULL,
    actor       TEXT NOT NULL,
    reason      TEXT NOT NULL DEFAULT '',
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 同一缺陷在多车型/多版本复现 → 关联多条执行记录（合并去重的依据）
CREATE TABLE defect_links (
    id           BIGSERIAL PRIMARY KEY,
    defect_id    BIGINT NOT NULL REFERENCES defects(id),
    execution_id BIGINT NOT NULL REFERENCES executions(id),
    UNIQUE (defect_id, execution_id)
);

-- ═══════════════ ④ 日报汇总（对账的一方）═══════════════
CREATE TABLE daily_exec_summary (
    id          BIGSERIAL PRIMARY KEY,
    biz_date    DATE NOT NULL,
    project_id  BIGINT NOT NULL REFERENCES projects(id),
    version_id  BIGINT NOT NULL REFERENCES versions(id),
    total       INTEGER NOT NULL DEFAULT 0,
    passed      INTEGER NOT NULL DEFAULT 0,
    failed      INTEGER NOT NULL DEFAULT 0,
    blocked     INTEGER NOT NULL DEFAULT 0,
    UNIQUE (biz_date, project_id, version_id)
);

-- ═══════════════ ⑤ 幂等 ═══════════════
CREATE TABLE idempotency_keys (
    id          BIGSERIAL PRIMARY KEY,
    scope       TEXT NOT NULL,          -- claim_task / submit_result / create_booking
    key         TEXT NOT NULL,
    body_hash   TEXT NOT NULL,          -- 同 key 换 body → 422
    status_code INTEGER NOT NULL,
    response    JSONB NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (scope, key)                 -- ← 幂等唯一防线
);

-- ═══════════════ ⑥ 本地消息表（跨项目同步/汇总异步化）═══════════════
CREATE TABLE outbox (
    id         BIGSERIAL PRIMARY KEY,
    topic      TEXT NOT NULL,           -- exec_result_recorded / slot_released
    payload    JSONB NOT NULL,
    status     TEXT NOT NULL DEFAULT 'pending',   -- pending|done|dead
    attempts   INTEGER NOT NULL DEFAULT 0,
    next_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_error TEXT NOT NULL DEFAULT ''
);
CREATE INDEX ix_outbox_due ON outbox (status, next_at);

-- ═══════════════ ⑦ 对账差异 ═══════════════
CREATE TABLE recon_discrepancies (
    id         BIGSERIAL PRIMARY KEY,
    biz_date   DATE NOT NULL,
    project_id BIGINT NOT NULL,
    kind       TEXT NOT NULL,
    expected   INTEGER NOT NULL,
    actual     INTEGER NOT NULL,
    detail     JSONB NOT NULL DEFAULT '{}'::jsonb,
    resolved   BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (biz_date, project_id, kind)
);
```

**设计要点（面试会问）**

| 点 | 为什么 |
| --- | --- |
| `vehicle_slots` 唯一约束 `(vehicle_id, slot_date, half)` | **"同一台车同一半天只能有一个占用"由 DB 保证**，不靠应用层判断 |
| 半天粒度而非分钟 | 规避区间重叠计算（见 §1.3） |
| `bookings` 用**部分唯一索引** `WHERE status='active'` | 取消的预约要能释放档期，但历史记录要留 |
| `execution_queue.version` 乐观锁 | 领取是"抢占"，必须 `WHERE status='pending' AND version=?` |
| `defect_links` 多对多 + 唯一 | 同一缺陷多车型复现可合并，且不会重复关联 |
| `idempotency_keys(scope,key)` 唯一 | 幂等靠 DB 约束（不是进程内字典） |
| `CHECK (half IN (0,1))` + `UNIQUE` | 脏数据在 DB 层就写不进去 |

| 方法 | 路径 | 说明 | 幂等 |

| POST | `/v1/executions` | 提交执行结果（可同时带缺陷） | 必需 |

## 四、六个技术点：方案 + 实验 + 验收

### 4.1 车辆档期不被重复占用（对应"库存不超发"）

| 方案 | 实现 | 适用 |
| --- | --- | --- |
| **A 条件更新（推荐）** | `UPDATE vehicle_slots SET status='booked', booking_id=:b, version=version+1 WHERE vehicle_id=? AND slot_date=? AND half=? AND status='free'` → affected=0 即被占 | 默认方案，单语句原子 |
| **B 悲观锁** | 事务内 `SELECT ... FOR UPDATE` 再判断 | 需要"先查后改"逻辑时（如连续占多个半天） |
| **C 预占 + 确认** | Redis Lua 预占档期，DB 异步落 | 峰值场景，有一致性窗口 |

**实验**：1000 并发抢**同一台车同一个半天**

| 指标 | 目标 |
| --- | --- |
| **重复占用数** | **0** |
| 成功预约数 | **恰好 1** |
| 失败原因分布 | 全部是 `slot_not_available`（而不是 500/死锁） |
| P99 | 三种方案对比 |

> 报告写成："单档期用 A（一条 UPDATE 就够，P99 X ms）；连续占多半天用 B（固定加锁顺序防死锁）；C 只在抢购式场景用。"

### 4.2 执行任务领取幂等（抢占）

```sql
-- 领取：抢占式，必须"恰好一人成功"
UPDATE execution_queue SET status='claimed', claimed_by=:t, claimed_at=now(), version=version+1
WHERE id=:id AND status='pending' AND version=:v;
```

**实验**：20 个测试员并发领**同一条**任务，同 `Idempotency-Key`

| 指标 | 目标 |
| --- | --- |
| `claimed_by` 最终只有一个 | ✅ |
| 成功数 | **恰好 1**，其余返回 409 `already_claimed` |
| 同 key 重放 | 返回**同一个** `execution_id`（幂等生效） |
| 换 body 同 key | **422**，且不产生任何状态变更 |

### 4.3 缓存一致性（车辆/用例详情）

| 方案 | 脏读窗口 |
| --- | --- |
| A Cache-Aside 删缓存 | 并发下"读旧值回填"仍脏 |
| B 延迟双删 | 窗口变小，非 0 |
| C outbox 驱动删缓存 | **最终一致** |

**实验**：200 写 + 200 读并发 30s，结束校验缓存 == DB。
指标：最终不一致条数（应 0）、**过程脏读次数**（A>B>C）、缓存命中率、P99。

> **必须做负对照**：先跑"故意不删缓存"的版本，证明实验**能测出**脏读；否则"全程 0"可能是实验没打中窗口。

### 4.4 执行结果异步汇总（跨表最终一致，不引 MQ）

```
事务：写 executions + 写 outbox(exec_result_recorded)   ← 同一事务，原子
worker：轮询 outbox → upsert daily_exec_summary → 置 done
失败：attempts+1，指数退避；> 5 次 → dead + 告警（可人工重放）
```

**实验**：注入 worker 失败 30s → 恢复后

| 指标 | 目标 |
| --- | --- |
| 汇总与明细最终一致 | **差异 0** |
| 重试次数 / dead 消息 | 记录，且 dead 可重放成功 |
| 期间汇总表 | 不能出现"少算"且无法追溯 |

### 4.5 问题单状态机

```
open → triaged → assigned → fixing → verifying → closed
  ↓        ↓         ↓         ↓         ↓
rejected  rejected  rejected  reopened  reopened
```

- 显式转移表；非法转移 **409**；每次转移写 `defect_transitions`
- **幂等**：重复提交同一 to_status → 200 + `already=true`，不重复写审计

**实验**：遍历所有 (from,to) 组合 → 合法全过、非法全 409、**审计条数 == 合法转移数**

### 4.6 日终对账（三方对齐）

```
① 明细侧：executions 按 (项目, 版本, 日, result) 聚合
② 汇总侧：daily_exec_summary
③ 质量侧：result='fail' 的执行**必须**有一条关联问题单（defect_links 或 defects.execution_id）
```

差异类型：

| kind | 含义 | 业务后果 |
| --- | --- | --- |
| `summary_mismatch` | 汇总 ≠ 明细聚合 | 日报口径错，向上汇报失真 |
| `missing_summary` | 有明细无汇总 | 少算 |
| `extra_summary` | 有汇总无明细 | 多算/脏数据 |
| **`fail_without_defect`** | **失败但没提单** | **质量问题被漏掉（真实硬规则）** |

**实验**：注入 5 种差错（漏汇总、多汇总、数字改错、失败未提单、跨日）→ **检出 100%**、误报 0

> `fail_without_defect` 这条是**业务规则型的对账**，不只是数字对账——面试里讲这个会让人眼前一亮。

### 4.7 深分页（问题单 50 万条）

| 方案 | 1 万页 P99 |
| --- | --- |
| `LIMIT 20 OFFSET 200000` | 慢（扫+丢弃） |
| **Keyset** `WHERE (created_at,id) < (:t,:id) ORDER BY created_at DESC, id DESC LIMIT 20` | 快（索引定位） |

必须配 `ix_defects_keyset (created_at DESC, id DESC)`；附 `EXPLAIN (ANALYZE, BUFFERS)`。

## 七、面试问答映射

| 面试官会问 | 答案要点 |
| --- | --- |
| 怎么防止两个项目抢同一台车？ | 唯一约束 + 条件更新（`WHERE status='free'`）；1000 并发实测**重复占用 0** |
| 为什么用半天粒度？ | **业务决定的**，规避区间重叠；如果业务要分钟级我会用 `tsrange` + GiST 排他约束 |
| 抢占式领取怎么保证只有一人？ | `WHERE status='pending' AND version=?` 原子更新 + affected 判定，**实测 20 并发恰好 1 人** |
| 幂等怎么做的？ | DB 唯一约束 + 同事务 + body_hash；同 key 20 并发只生效 1 次 |
| 缓存一致性？ | 三方案脏读窗口对比 + **负对照证明实验有效** + 最终不一致 0 |
| 分布式事务？ | 本地消息表 + 补偿 + dead 重放；主动说什么时候该上 MQ |
| 对账怎么做？ | 三方对齐 + **`fail_without_defect` 这种业务规则型对账** |
| 深分页？ | keyset + 复合索引 + `EXPLAIN` + 1 万页 P99 |
| 你怎么保证没 bug？ | 并发测试 + DB 层 CHECK/唯一约束兜底 + 对账兜底（三道防线） |

## 八、项目起源话术（**真话版**）

> "我在比亚迪负责测试与用户版本数据的分析。日常最大的痛点是：**测试车辆、软件版本、用例、问题单这四个维度的数据散在不同表里，取一次数要手工拼半天**；而且经常出现'同一台测试车被两个项目同时排期''同一个用例两个人同时领''执行失败了但没人提单'这类问题。
>
> 我虽然不负责系统开发，但想搞清楚这些问题的技术本质，就自己做了一个测试数据管理平台。做完最大的收获是两点：
>
> 第一，**资源占用的正确性应该由数据库保证，而不是应用层判断**——我用 `(车辆, 日期, 半天)` 唯一约束 + 条件更新，1000 并发抢同一档期也只会成功一次。
>
> 第二，**对账不只是对数字**。我加了一条'执行失败但没有关联问题单'的检查——这是质量规则，不是数据一致性，但它才是最容易被漏掉的。"

**为什么这个话术可信**：痛点是真实的、业务细节是真实的、技术实现是真实的。面试官追问"你们当时怎么排车的""日报口径怎么定的"，你都答得出来。

## 九、附录：预期会踩的坑（提前写进 README）

| # | 坑 | 预期根因 |
| --- | --- | --- |
| 1 | 并发下出现两条 active 预约 | 唯一索引写成了普通索引，或没加 `WHERE status='active'` 导致部分索引失效 |
| 2 | 领取接口偶发"两人都成功" | 只查了 `status` 没比对 `version`；或先 SELECT 再 UPDATE（非原子） |
| 3 | 缓存一致性"全程 0 不一致"却是假的 | 读并发没打中失效窗口 → **必须做负对照** |
| 4 | 对账每天都有噪声差异 | 时区/`executed_at` 与 `biz_date` 口径不一致（UTC vs 本地日期） |

> 第 4 条是真坑：日报按"自然日"切，但 `executed_at` 是 `TIMESTAMPTZ`。不统一时区口径，每天都会差几条。
