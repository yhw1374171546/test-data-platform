# 实验报告 · 工程化（Alembic / HTTP 层压测 / 多 worker）

> 技术主线 7 个技术点做完之后补的三件事，都是"能跑"和"能交给别人跑"之间的差距：
>
> 1. **Alembic 化**：`001_baseline.sql` + 幂等 `002_*.sql` 能跑，但**不知道库是什么版本**，
>    也没法回滚/增量演进。
> 2. **HTTP 层压测**：之前 8 个 bench 全走 service 层，P99 不含 uvicorn / 序列化 / socket。
> 3. **多 worker 实测**：`SKIP LOCKED` 写好很久了，但只跑过单进程 —— 多副本到底行不行，得测。

## 1. Alembic 化

### 1.1 改了什么

| 之前 | 现在 |
| --- | --- |
| `init_db.py` 里判断 `tables==0` 就跑 `001_baseline.sql`，然后每次重跑 `002_*.sql` | `init_db.py` 调 `alembic upgrade head` |
| 没有版本表，不知道库是新是旧 | `alembic_version` 表记录 `0002_perf_indexes` |
| DDL 散在 `migrations/versions/*.sql`（和 py 混在一起） | DDL 统一在 `migrations/sql/*.sql`，`migrations/versions/*.py` 只做"读文件 → 执行" |
| 只能前进 | `downgrade` 可用（基线除外） |

**为什么 DDL 还留在 `.sql` 里，而不是搬进 Python 字符串**：
`psql -f migrations/sql/001_baseline.sql` 能直接跑，DBA 不用懂 Alembic；
迁移脚本只是"版本编排"，不重复维护一份 DDL。

**为什么不做 autogenerate**：项目没有 ORM 模型（表是手写 SQL 建的），
`target_metadata = None`，所以 `alembic check` / `--autogenerate` 会明确报错。
加迁移的方式是 `alembic revision -m "..."`，然后在 `upgrade()` 里写 SQL。

### 1.2 三种库都要能处理

| 库的状态 | `init_db.py` 的行为 | 实测输出 |
| --- | --- | --- |
| **全新库**（一张表都没有） | `upgrade head`：依次跑 0001 + 0002 | `schema 已执行全部迁移：0002_perf_indexes（17 张表 / 42 个索引）` |
| **老库**（有表、没有 `alembic_version`） | 先 `stamp head` 再 `upgrade`（跳过 DDL） | `schema 老库没有版本表，已 stamp 到 head：0002_perf_indexes` |
| **已是最新** | `upgrade` 是空操作 | `schema 已是最新版本：0002_perf_indexes` |

老库这条路是刻意做的：本机这个库就是在 Alembic 之前建的，
如果直接 `upgrade` 会因为"表已存在"而失败 —— 那时候只能删库重来，代价太大。

`--drop` 是唯一破坏性操作（删库 → 重建 → 迁移），专门给"我想从头来一遍"用。

### 1.3 顺手踩的两个坑

| 坑 | 根因 |
| --- | --- |
| `alembic.ini` 里写中文注释，`alembic current` 直接崩 `UnicodeDecodeError: 'gbk'` | `configparser` 读 ini 用的是**系统 locale 编码**（中文 Windows 是 GBK），不认 UTF-8 声明。**ini 只能放 ASCII**，说明写进 `env.py`（py 文件一定按 UTF-8 读） |
| 迁移里 `op.execute(整个 .sql)` 报 `cannot insert multiple commands into a prepared statement` | `op.execute` 走 psycopg3 的**扩展协议**；把 SQL 一次性交给 `cursor.execute()` 且带参数时，PG 不允许一次多条。改成 `op.get_bind().connection.dbapi_connection.execute(sql)`（无参数 → 简单查询协议，天然支持多语句） |

## 2. HTTP 层压测

### 2.1 结果（50 并发）

```text
[service 层] 同一档期 50 并发：{'created': 1, 'slot_taken': 49}  耗时 0.36s
[HTTP 层]    同一档期 50 并发：{'409:slot_not_available': 49, 'created': 1}  耗时 3.15s  16 req/s

  场景                          P50      P95      P99      max          吞吐
  写·service 层              150.4ms   284.7ms   297.4ms   297.4ms      140/s
  写·HTTP 层                 282.8ms   375.7ms   378.6ms   378.6ms       16/s
  读·HTTP（缓存命中）           63.4ms    96.5ms   105.3ms   112.2ms      258/s
```

| 校验 | 结果 |
| --- | --- |
| service 层：恰好 1 人成功 | ✅ |
| **HTTP 层：恰好 1 人成功**（并发语义没被框架破坏） | ✅ |
| HTTP 层：其余全部 `409 slot_not_available` | ✅ 49/49 |
| HTTP 层没有 5xx 或异常 | ✅ |
| 缓存读全部命中（`X-Cache: hit`） | ✅ 1000/1000 |

### 2.2 那个 +80ms 不是"uvicorn 慢"

HTTP 层比 service 层的 P99 高 **57~81ms**（两次运行）。原因不是解析或序列化，而是**两级排队**：

```text
50 个请求 → anyio 线程池（默认 40 个线程，同步 endpoint 在这里执行）
          → 每个线程要一条 DB 连接（池子 20+20=40）
          → 还要抢同一行的行锁（这才是大头）
```

service 层的一次调用只排"连接池"一次，HTTP 多排了"线程池"一次。
**这就是为什么生产上要么调大 `--limit-concurrency` / 线程池，要么直接起多个 uvicorn worker 进程** ——
同步 endpoint 的并发上限首先是被线程池卡住的，不是被 CPU。

读场景（走缓存、不碰 DB）的 P99 是 105ms，看起来也不低，但它含 uvicorn + 50 个 Python 线程的
GIL 调度 —— **绝对值不要当基准线用**，能说明的是"缓存在 HTTP 这一层确实生效、没有 5xx"。

## 3. 多 worker 实测

### 3.1 怎么证明"没有重复处理"

`FOR UPDATE SKIP LOCKED` 的效果不能靠"看起来没报错"判断。用两个硬指标：

1. **`attempts` 恰好 1**：每条消息成功时 `attempts` 只 +1；如果两个 worker 都处理了同一条，
   必然出现 `attempts >= 2`。
2. **`daily_exec_summary.total` 恰好等于消息数**：汇总用的是"重算"而不是"累加"，
   所以即使重复消费也不会多算 —— 但 `attempts` 会暴露重复消费本身。

### 3.2 结果

```text
多 worker 实测 · 4 个进程 × 200 条消息

  单 worker：2.21s，done=200，attempts_max=1
  4 个 worker：1.44s，done=200，attempts_max=1
  并行加速：1.54x（2.21s → 1.44s）

  [OK] 4 个 worker 全部正常退出：exit=[0, 0, 0, 0]
  [OK] 所有 200 条消息都处理完了：done=200 pending=0
  [OK] 没有死信：dead=0
  [OK] **没有重复处理**（每条消息 attempts 恰好 1 次）：attempts<>1 的消息数=0
  [OK] 汇总 total 恰好等于消息数（没有被多算）：total=200
  [OK] 汇总 passed/failed/blocked 与预期一致：{'passed': 50, 'failed': 50, 'blocked': 50}
  [OK] skip 被算进 total（total - 三者之和 == skip）：推算 skip=50 预期=50
  [OK] 明细与汇总无差异：diff_count=0
```

**加速比只有 1.54x 而不是 4x**，原因是这批消息太小：每个 worker 的启动、抢连接、
退出占了大部分时间。要更强的扩展性，要么把批大小调大，要么让 worker 常驻。
**但正确性必须是 1x**：没有一条消息被处理两次，汇总也没有被重复累加。

（小技巧：跑多 worker 时把每个进程的 `TDP_POOL_SIZE` 调到 5 —— 4 个 worker × 默认 40 条连接
会直接打满 PG 的 `max_connections=100`。）

### 3.3 顺手踩的坑

`diff_summary()` 返回的是**字典** `{"mismatched": [...], "missing": [...], "extra": [...], "diff_count": 0}`，
第一版断言写成 `len(diffs) == 0` —— 恒为 4（四个键），于是"有差异"永远成立。
要用 `diffs["diff_count"]`。

## 5. 仍然没做的

| 项 | 说明 |
| --- | --- |
| Alembic 的 autogenerate | 没有 ORM 模型，只能手写迁移；如果以后上了 SQLAlchemy 模型再打开 |
| 滚动升级 / 零停机迁移 | `CREATE INDEX` 用的是普通锁（小表没事）；线上大表要 `CONCURRENTLY`（不能在事务里跑，Alembic 需要 `autocommit_block`） |
| HTTP 压测的容量结论 | 只做了"单进程 uvicorn"，没测多进程/多机；也没压到饱和点找瓶颈 |
| 多 worker 的故障场景 | 只测了正常路径；worker 中途被 kill 时消息会留在 `processing` 吗？（本实现是事务内完成，kill 会整体回滚，消息仍是 pending） |
