# 实验报告 · 缓存一致性（A/B/C + 负对照）

> 目标：技术方案 §4.3 —— 三种缓存失效方案对比，**必须带负对照**，
> 验收线是"最终不一致 0，过程脏读次数 A > B > C"。
>
> **实测结论与技术方案预期相反**：同步删（A/B）脏读率 1%~4%，消息驱动（C）~11%，
> 而 C 的优势在"失效不会丢、窗口有界"，不在"次数少"。机制见第 5 节。
> 这是本报告最有价值的部分：实验做出来和预想不一样，才有信息量。

## 2. 三种方案 + 负对照

| 策略 | 实现 | 代码位置 |
| --- | --- | --- |
| `none`（负对照） | 有缓存但**从不失效** | `catalog.after_commit_invalidate` 空转 |
| `delete`（A） | 事务**提交后**删 key | 同上，`cache.delete` |
| `double_delete`（B） | 写前删一次 + 提交后**延迟 50ms** 再删 | `cache.schedule_delayed_delete` |
| `outbox`（C） | 写事务里插 `cache_invalidate` 消息，worker 消费后删 | `catalog.enqueue_invalidation` + `outbox.process_cache_invalidations` |

三个实现细节值得单独说：

**① 删缓存必须发生在事务提交之后。**
在事务里删、事务回滚，只是白删一次（可接受）；但如果"删早了、随后又被回填旧值"，就留下脏值。
A/B/C 都遵守这个顺序（B 的写前删是额外的一次，不替代提交后删）。

**② C 的失效消息不会丢。**
`cache_invalidate` 和业务写入在同一个事务里落 `outbox`，删 key 失败（Redis 挂了）会抛异常让消息重试，
超过 `max_attempts` 进死信 + 告警。**A/B 的删除是"尽力而为"**：进程在 commit 之后、delete 之前崩掉，
那次失效就永久丢了 —— 只能等 TTL。

**③ C 必须批量消费。**
每条消息一个事务时，实测消费吞吐只有 ~100 条/秒，而写入是 ~460 次/秒，积压一路涨，
C 会退化成"从不失效"。改成"一次事务取一批、一次删一批 key"后，消费能跟上（本轮 4034 条全消费）。
**批量不是优化项，是这类消息的标配。**

## 3. 脏读怎么判定（必须严谨，否则数字没有意义）

给每次写入一个递增序号，写进 `location = "L{seq}"`。写线程在**事务提交之后**把
`(车, seq, 提交完成时刻)` 记到日志里；读线程：

```text
t0     = 开始读的时刻
served = 读到缓存/回源拿到的 L{k}
committed = 这台车"提交时刻 <= t0"的最大 seq

k < committed  →  脏读
（读请求开始时，更新的值已经提交了，但读返回的是更旧的值）
```

这个判定有两条刻意的设计：

- **按车（per-vehicle）比较**。第一版用了全局最大序号，而读回来的是某一台车 ——
  拿"全局最大"去比"单车序号"，正常读也被判成脏读（各策略都测出 40%~99% 的假脏读）。
- **保守**。日志时间戳在锁内采集，只会比真实提交时刻**更晚**，
  所以只会少报、不会虚报。宁可低估脏读，也不制造假数据。

## 5. 实测：同步删 ≪ 异步删 ≪ 不失效

技术方案预期是 A（删缓存）最差、B（延迟双删）居中、C（outbox）最好。实测的稳定结论是另一回事：

| 方案 | 脏读率（两次运行） | 单次最大滞后 | 停写后残留 | 失效会不会丢 |
| --- | --- | --- | --- | --- |
| none | 99.65% | 1.2 万个版本 | 8/8 | —（从不失效） |
| **A 同步删** | **1.72% / 1.60%** | 5 | 1/8 → 0/8 | 会丢（崩溃即永久脏，等 TTL） |
| **B 延迟双删** | **4.30% / 1.02%** | 6 | 0/8 | 会丢 |
| **C 消息驱动** | **10.12% / 11.36%** | 98 / 74 | 0/8 | **不会丢**（重试 + 死信） |

三句话把机制说清楚：

**① 同步删（A/B）为什么脏读少。**
删除和提交在同一个调用里，间隔亚毫秒，窗口极窄。唯一的窗口是"读者读到旧值、
回源后回填、恰好落在删除之后"——概率低。
**代价是那条偶发的脏值会一直留到 TTL**：第一次运行 A 组停写后仍有 1/8 条脏值，
它就是一条"丢失的删除"。进程如果在 commit 之后、delete 之前崩掉，同样只能等 TTL。

**② B 的"写前删"不总是更好。**
写前把缓存清空后事务还在进行，读者回源读到的是**旧值**并重新写回缓存，
要等延迟删除才清掉 —— 用一段"确定的旧值窗口"去换"窗口更短"。
本轮两次运行里 B 有时比 A 好、有时更差，就是这两种效应在互相抵消。
延迟双删真正的价值在"写事务很长"的场景，而不是"读多写多"。

**③ C 的次数最多，但它是最"可控"的。**
异步失效天然有**传播延迟**（本轮消费间隔 20ms）：这段时间每个读都读到旧值，
所以次数最多（~11%）；但每次滞后都有界（max_lag 74~98 = 消费延迟内积累的写入量），
而且**失效不会丢** —— 停写后残留 0，积压可查、可重试、可告警。

### 所以选型不是比"谁次数少"

| 方案 | 失败模式 | 可观测性 |
| --- | --- | --- |
| A/B | 罕见的**永久**脏值（丢删除，只能等 TTL） | 差：丢了你也不知道 |
| C | **有界**的脏值（= 消费延迟） | 好：outbox 积压 / lag 可监控，消息可重试 |

一句话：**A/B 是"少而可能永久错"，C 是"多但有界、可解释"**。
生产上三者都必须有 TTL 兜底 —— 两次运行里四组在 TTL 兜底后都收敛到 0。

## 6. 线程数为什么用 20/20 而不是技术方案写的 200/200

这台机器 16 核。跑 100 读 + 100 写时 CPU/GIL 饱和，测出来的延迟是**调度噪声**：

```text
[1/4] none   写 14259 / 读   1308   p50 573.91ms  p99 3274.89ms   （读线程几乎被饿死）
[4/4] outbox 写  2198 / 读  51455   脏读 83.50%，max_lag 3877     （消费线程也被饿）
```

同样是"消费跟不上"的另一种形态：不是代码慢，是机器跑不动 200 个 Python 线程。
所以正式数据用 20/20，并在报告里如实保留这组 100/100 的观察 ——
**它说明 C 的窗口直接由"消费能不能跟上"决定**，跟理论推导一致。

## 9. 本项**没有**做的

| 项 | 说明 |
| --- | --- |
| 缓存穿透 | 不存在的车会被反复回源。生产要加空值缓存（短 TTL）或布隆过滤器 |
| 缓存击穿 | 热点 key 过期瞬间大量回源。要加互斥重建（单飞） |
| 多副本 | 单进程 Redis 客户端；多副本下失效消息的消费要用 `SKIP LOCKED`（已支持）+ 消费 lag 监控 |
| 缓存与 DB 的强一致 | **做不到也不该做**。真要强一致就别缓存（`off` 策略），或者用"读主库" |
| p99 归因 | 本轮 p50/p99 含连接池排队与 Python 调度，只能横向比，不宜当绝对延迟 |
